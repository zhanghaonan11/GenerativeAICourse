# AI 智能体

## 概述：从手动到自主

今天大多数软件都需要人类点击界面、做决策或手动执行工作流程。

想想客服团队手动审核退款请求。

我们试图用传统的自动化工具来解决这个问题，但它们只能用于完全可预测的工作流程，因为它依赖于一系列 if 和 else 语句。

然而，很多业务流程是复杂的、不可预测的，需要动态决策。

许多人将 AI 智能体定义为可以采取行动的大语言模型。历史上，大语言模型是关于生成响应的，智能体是关于执行行动的。

**但从第一性原理来说，AI 智能体只是一个使用大语言模型作为决策引擎来独立执行行动的应用程序。** 关键词是独立——它不依赖你来采取行动（告诉它该做什么）。

退款审批 AI 智能体是一个可以采取行动的应用程序（就像所有应用程序一样），如批准退款、转发给人工、执行退款等。唯一的区别是做这些决策的不是人类，而是大语言模型。

### 传统自动化 vs AI 智能体

你可以使用传统自动化用简单逻辑构建退款审批流程，如：
```
If amount > $500 AND no manager approval THEN reject
```

使用 AI 智能体，它可以审查客户的购买历史，考虑退货原因，在上下文中评估公司政策，然后做出决定。智能体可以识别工作流程完成（退款已处理，客户已通知），并且可以自我纠正（我发送了错误的退款金额，让我发起一个更正）。

## 为什么 AI 智能体突然爆发

1. **决策能力：** 推理模型的兴起使 AI 智能体能够做出复杂的决策。
2. **通信协议：** MCP 等通信协议的兴起（下一模块会详细介绍）使构建复杂智能体的过程变得简单得多。

### 微软对智能体的定义和愿景

我们在微软定义智能体的方式，以及我们用来为客户构建产品和功能的参考框架，是**人类可以将任务委托给的系统，而且这些任务会随着时间的推移变得越来越复杂**。

**推理：** 由于推理模型的兴起，智能体现在能够执行越来越复杂的任务，特别是软件工程。

### 智能体网络

**运行时组件：**
- **推理层：** 决定采取什么行动的核心决策能力
- **记忆：** 这是基础软件工程。我们已经探索了像 RAG 和长上下文窗口这样的解决方案，还有正在进行的开发如 Talk 智能体。目标是记住交互并像上次一样解决问题——就像你期望从你委托任务的人那里得到的一样
- **工具：** 允许智能体在世界中采取行动的实际能力

**协议：**
- **MCP（模型上下文协议）：** 你需要智能体采取行动，这意味着它们必须与其他系统通信。MCP 就像 AI 智能体的 HTTP——它提供了一种标准化的方式让智能体与不同的服务和工具交互
- **A2A（智能体对智能体）：** 使智能体能够协同工作的通信协议

## 何时构建 AI 智能体

### 1. 复杂决策
当工作流程需要无法用规则捕捉的判断。例如，传统系统可能会自动批准 50 美元以下的退款，但智能体可以评估一个客户已经退货 3 次的 45 美元退款请求。

### 2. 无法维护的规则系统
如果你的规则系统已经增长到数百个条件语句。

### 3. 非结构化数据工作流程
如果你正在处理文档、电子邮件或自然语言。例如，保险理赔智能体可以阅读事故报告、医疗记录等。这是传统解析无法做到的。

### 经济计算
智能体当然比传统自动化每次操作成本更高，但它们消除了复杂决策所需的人工劳动。如果你每小时支付 50 美元给人审核案例，而智能体每个案例可以处理 2 美元，并且你每月处理 1000 个案例，你每月节省 48,000 美元减去 2,000 美元的智能体成本。

## 智能体的组件

### 1. 模型（大脑）
这是大脑。不同的模型有不同的能力和不同的成本。总是用最强大的模型构建你的原型以建立性能基线，设置评估指标（准确性和任务完成率），然后在可接受的结果保持的情况下用较小的模型替换。

通常，较大的模型用于复杂的决策点。例如，使用 SLM 进行简单的数据检索（获取客户订单历史），但使用 LLM 进行退款决策（我们是否应该批准这个本月已退货 5 件商品的客户的 500 美元退款）。

### 2. 工具
它们可以是数据工具如数据库查询，可以是通信工具如发送电子邮件或数据修改（更新 CRM 记录），或者可以是编排工具如调用另一个智能体。每个工具需要在你的代码中有标准化的定义，有明确的参数和返回值。糟糕的工具文档会导致智能体误用 API。

**注意：** 你可能听说过函数调用这个术语。函数调用和工具的区别是，工具是实际的实现（如执行工作的 Python 函数），而函数调用是大语言模型告诉你的应用"我需要访问天气函数"的能力。你在智能体中两者都需要，但 Semantic Kernel 抽象了函数调用，所以它们看起来可能是同一件事。

**示例：**
```python
@function_tool
def process_refund(customer_id: str, order_id: str, amount: float, reason: str):
    """
    Process a refund for a customer order.

    Args:
        customer_id: Unique customer identifier
        order_id: Order to refund
        amount: Refund amount in dollars (must be <= original order total)
        reason: Business reason for refund (required for accounting)

    Returns:
        {"success": bool, "refund_id": str, "message": str}
    """
    # Implementation here
    return {"success": True, "refund_id": "REF123", "message": "Refund processed"}
```

### 3. 指令
这定义了智能体如何行为，它被允许做什么，以及它应该如何处理边缘情况。不要编写新程序，而是调整你当前的政策。如果你的客服团队遵循 12 步退款流程，那就成为你的智能体的指令集。

也要捕捉边缘情况，如：如果客户提供部分信息怎么办？如果 API 调用失败怎么办？如果客户问的问题超出了你的领域怎么办？

## 编排器

一旦你有了一个带有模型、工具和指令的智能体，你需要从头到尾编排这些工作流程。单个大语言模型无法处理需要检查条件、调用多个工具并根据结果调整的多步骤过程。

### 单智能体系统
更容易构建，通常依赖于提示模板，不是为不同用例创建单独的智能体，而是使用一个接受变量的灵活提示。

### 多智能体系统
当需要复杂逻辑以及工具数量变大时使用。有两种主要模式：

1. **中心辐射模式：** 一个中央管理智能体协调专门的工作智能体
2. **去中心化模式（点对点）：** 没有中央协调者

前者用于当你需要综合多个智能体的结果或当你需要一个智能体与用户保持对话上下文时。

## 处理记忆

构建生产 AI 智能体最大的挑战之一是管理记忆。我们已经探索了如何解决对话记忆的问题，如总结过去的对话，或者甚至使用 RAG 进行更长期的存储。记住，大语言模型是无状态的——它们在 API 调用之间不记得任何东西，因为每个请求都是独立的。

另一种类型的记忆是**学习记忆**。理想情况下，我们希望智能体从所有过去的交互中学习，使其变得更好。这如何实现的一个例子是使用 RAG，所以我们存储成功的解决示例并在类似案例中检索它们。

## 智能体 RAG：超越传统检索

我们已经探索了传统的 RAG 系统。用户发送提示，我们检查向量存储中与提示相关的数据，将其与提示组合并发送到大语言模型。这种情况下大语言模型实际上只是总结答案，仅此而已。

但大语言模型有比仅仅总结提示和从向量存储检索的相关块更多的能力。**智能体 RAG** 是一种更复杂的 RAG 实现，当用户提问时，智能体分析问题，然后决定检索策略（也许我需要从向量数据库 2 和 3 获取数据），然后在检索到的信息上进行推理，然后检索更多，直到得到最终答案。所以它是 RAG 的更复杂形式。

## 护栏

AI 智能体可以采取影响真实客户的行动，它们可以访问敏感数据，它们可以代表你的品牌。与只生成文本的聊天机器人不同，智能体需要防止危险输出行动的保护。

你需要平衡。过于严格的护栏可能会阻止合法的用户请求。但商业现实是，一次泄露的客户数据库或一次未经授权的 10,000 美元退款可能比数月的护栏开发成本更高。

### 护栏类型

1. **相关性分类器：** 这使智能体在其预期范围内工作。所以它防止客服智能体回答随机问题而不是解决客户问题。SLM 通常用于分类输入相关性。

2. **安全分类器：** 检测提示注入和越狱尝试。通常使用在提示注入模式上微调的模型。

3. **PII 过滤器：** 防止意外暴露 PII 信息。

4. **内容审核过滤器：** 阻止有害内容，包括仇恨言论或骚扰。可以使用 OpenAI 的审核 API。

5. **人工干预：** 对于可能不需要人工干预的低或中等风险任务（如发送电子邮件、更新客户记录）。人工批准可用于高风险任务如处理退款或取消订单。

6. **基于规则的保护：** 这是为了快速阻止已知威胁。如 SQL 注入过滤器、输入长度限制、字符编码过滤器（防止基于 Unicode 的攻击）。

7. **输出验证：** 确保智能体响应符合品牌指南和业务政策。如语调分析、政策合规、法律合规等。

### 构建护栏的策略

**阶段 1：** 专注于数据隐私和内容安全。这些是可能造成即时业务损害的最高影响风险（PII 暴露、提示注入、损害品牌形象的有害内容）。

**阶段 2：** 根据真实世界的失败添加护栏。监控你部署的智能体并为遇到的实际问题实施护栏，如用户试图通过社会工程获得免费产品。

**阶段 3：** 优化安全性和用户体验。减少阻止合法请求的误报，根据用户上下文自定义护栏敏感度（VIP 客户得到不同待遇）。

### 人工干预
护栏很好，但目前智能体仍然需要人工干预。即使是完全自主的智能体，你也需要人类在需要时可用，这在你超过失败阈值或进行高风险行动时触发。

## 从头构建智能体 vs 使用"托管"智能体如 Azure AI Agent

你可以使用 Semantic Kernel 从头构建 AI 智能体，自己管理工具访问（自己写代码）或记忆等。或者你可以使用 Azure AI Agent 这种托管服务。它是在 Azure 上运行的基础设施。微软管理服务器、持久存储（如文件存储、对话线程和向量数据库都是服务器端管理的）、内置工具如代码解释器都运行在微软的安全环境中，以及与 AI 搜索、函数等的企业集成。

你当然可以使用 Semantic Kernel 与标准大语言模型 API，但你需要自己管理对话状态管理、工具执行和安全、扩展、向量数据库等。Azure AI Agent 可以为你处理所有这些，但你可能担心更高的成本或供应商锁定。当然，Semantic Kernel 可以用来连接 Azure AI Agent 服务。
