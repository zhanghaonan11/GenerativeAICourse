# RAG（检索增强生成）

## RAG 解决的问题

AI 模型是在截止到特定日期的公开数据上训练的。它们无法访问训练数据之外的信息——这包括你的私有公司数据、超出训练截止日期的最新信息，或任何不在其训练数据集中的专业知识。

问题是：我们如何在模型未被训练的数据上利用 AI 模型的推理能力？例如，帮助客户在你的目录中找到产品，或对公司内部文档进行推理。

## RAG 的工作原理

我们所做的是将这些私有文档转换为更小的块（稍后会详细介绍），使用嵌入 AI 模型将这些块转换为向量（一系列捕捉这些块的情感和含义的数字），我们将这些向量块存储在向量数据库中。然后，当用户询问关于这些私有文档的问题（例如："推荐给我适合攀登珠穆朗玛峰的产品"）时，我们将用户问题转换为向量（同样捕捉问题的情感和含义），将该向量与存储在我们向量数据库中的向量进行比较，然后最终将用户问题和返回的块向量（来自向量比较）一起提供给模型。

![image](https://github.com/user-attachments/assets/567589c9-4282-4a86-86d5-d9ea098e909f)


**所以从第一性原理来说：RAG 实际上是构建一个函数，当用户提问时，我们将问题转换为向量，将其与向量数据库中的向量进行比较，然后一旦找到相关向量，我们将其与提示一起添加到问题中。就是这么简单。**

## 为什么需要分块

数据被分块的原因是上下文窗口。上下文窗口有限制，如果数据超过这个限制（在大多数情况下会超过），那么我们就将其分成块。向量搜索在聚焦的信息上也能更好地工作。注意，当我们说向量搜索时，我们通常指的是语义词搜索，而不是传统的关键词搜索。

## 搜索类型：向量搜索 vs 关键词搜索 vs 混合搜索

**向量搜索**很好，但可能会错过精确的关键词匹配（可能太智能了，返回相关但不是精确匹配的内容）。

**关键词搜索**在精确关键词匹配方面很好。当然，它无法理解语义关系。

这就是为什么**混合搜索**很常见——它结合了两种技术以获得更好的整体检索质量。文档按组合分数重新排序，让你两全其美。

实际上有分块策略来确定最合适的块大小。这是一个权衡：如果太小会缺乏上下文，但如果太大会稀释相关信息。

一些向量数据库，如 Azure AI Search 为例，会为我们处理分块。我们将在这个例子中用代码来实现。

## RAG 索引：质量的基础

你的 RAG 系统的质量取决于你如何索引数据。

### 什么是索引

当你有大量数据集合时，搜索它可能是一个挑战。最直接的方法是使用线性搜索，但在规模上，这变得太慢了。

索引创建一个单独的数据结构，将可搜索的条件映射到数据的位置。所以不是扫描所有数据，我们首先扫描索引以确定相关数据存储在哪里，并只检索这些部分。

### 真实世界示例：制药公司

例如，一家制药公司创建了一个索引映射：

```
"drug_interactions" → [doc_3, doc_127, doc_2891, doc_5643, doc_8901]
"clinical_trials" → [doc_45, doc_298, doc_3372, doc_7123]
"adverse_reactions" → [doc_12, doc_567, doc_4321, doc_9876]
"pharmacokinetics" → [doc_78, doc_1456, doc_6789]
```

然后当科学家搜索药物相互作用时，它检查索引，只检索相关文档而不是搜索所有文档。

### 数据库索引示例

在关系数据库中为例，你可以创建一个索引，将列值（如工资、姓名、地址）映射到行位置（实际值）。

假设你有一个包含 50,000 名员工记录的表：

```sql
CREATE TABLE employees (
    emp_id INT,
    last_name VARCHAR(100),
    department VARCHAR(50),
    hire_date DATE,
    salary DECIMAL(10,2)
);
```

你可以在姓氏上创建一个索引：

```sql
CREATE INDEX idx_last_name ON employees(last_name);
```

这会创建一个看起来像这样的单独数据结构：

**索引结构（idx_last_name）：**
```
"Adams" → Row 15,847
"Brown" → Row 2,156
"Chen" → Row 41,923
"Davis" → Row 8,901
"Evans" → Row 33,412
... (按字母顺序排序)
"Wilson" → Row 7,234
"Young" → Row 28,567
```

现在，当你搜索 Adams 姓氏为例时，你可以快速检索它。

### RAG 索引上下文

在 RAG 的上下文中，就像在关系数据库中我们使用索引来避免扫描每一行一样，RAG 系统使用向量数据库索引来避免将你的查询与每个文档块进行比较。

在 RAG 系统中，索引质量影响你的 AI 是否能找到正确的信息来回答问题。糟糕的索引意味着 AI 获得不相关或不完整的上下文，这会导致错误或无用的响应。

## RAG 索引：3个关键层

### 1. 文档分块

你如何实际组织数据。你可以按字符限制来做，但这意味着你很可能会错过一些上下文或关键信息。因此，如前所述，使用语义分块。这些语义分割器使用语言模型。

### 2. 向量嵌入（将文本转换为数字）

通用嵌入可能检索不好的结果（例如，法律中的"IP"可能不被理解为知识产权）。领域特定的嵌入会带来更好的结果，比如在公司数据上微调的嵌入模型。

### 3. 向量数据库索引

## 相关性和质量控制

需要注意的一件事是，并非所有搜索结果都是相关的。你需要确定什么构成相关内容。

向量搜索有一个**相关性阈值**。如果你设置得太高（0.0），那么它可能会错过一些内容，但在错误信息可能代价高昂的高精度场景中很有价值。如果设置得太低，它可能会包含混淆模型的不相关上下文。你也需要一种方法来衡量这一点。

**用户满意度：** 用户是否获得了有用的信息？检索到的块实际上有多少是相关的？
