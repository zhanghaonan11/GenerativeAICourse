# LLMOps：端到端 AI 应用生命周期

## 什么是 LLMOps？

我们之前已经有了像 DevOps 这样的实践，它是一个用于开发、测试和部署包含一系列工具（如 GitHub、Jenkins 等）的应用程序的端到端框架。LLMOps 是一个类似的概念——它是开发、部署和维护基于 LLM 的应用程序的工具和流程的集合。

根本的区别在于，传统的 DevOps 处理的是确定性代码（相同的输入总是产生相同的输出），而 LLMOps 处理的是概率性 AI 系统，其中输出可能会有所不同，模型需要重新训练，且数据质量直接影响性能。

### 1. 数据策划：AI 成功的基石

这探讨了哪些数据是可用的，并概述了创建干净一致数据的数据转换过程。你需要丰富数据吗？你需要将数据与外部数据映射以丰富它吗？这都是数据策划过程的一部分。

**挑战：** 原始企业数据是杂乱、不一致且通常是不完整的。在任何 AI 模型能够有效工作之前，你需要将这些数据转换为产生可靠结果的格式。

#### 用于数据策划的 Azure 工具：

**Azure Data Factory (ADF):**
- **用途：** 编排来自多个来源的数据管道
- **能力：** 90+ 内置连接器、可视化管道设计器、自动调度
- **用例：** 从 SAP、Salesforce、Oracle、Excel 文件中提取数据，并转换为 AI 可用的格式

**Microsoft Fabric:**
- **用途：** 结合数据工程、数据仓库和实时分析的统一分析平台
- **能力：** OneLake 数据湖、Spark 笔记本、实时流处理、T-SQL 端点
- **用例：** 处理数百万条客户记录、清理交易数据、执行大规模复杂连接

**Microsoft Purview:**
- **用途：** 跨整个数据资产的数据治理、发现和血缘追踪
- **能力：** 自动数据分类、PII 检测、数据血缘可视化、数据目录
- **用例：** 编目所有企业数据源、跟踪合规性数据血缘、识别敏感数据

#### 真实实施案例：

**挑战：** 一家制造公司需要整理来自 8 个全球设施的 23 个不同系统的数据，用于预测性维护 AI。

**数据源：**
- SAP ERP（设备规格和维护历史）
- Historian 数据库（每 30 秒一次的传感器读数）
- CMMS 系统（工单和技术员笔记）
- Excel 电子表格（人工检查报告）
- IoT 传感器（实时温度、振动、压力数据）

**Microsoft Fabric 管道：**
1. **提取：** 
   - SAP 连接器通过数据工厂每晚提取设备数据
   - Event Hub 将实时 IoT 传感器数据摄入 Fabric OneLake
   - Blob 存储连接器处理技术员上传的 Excel 文件

2. **转换：**
   - Fabric Spark 笔记本标准化各设施的设备命名
   - 使用 Fabric 数据流将传感器读数转换为一致的单位
   - 使用 Azure AI 语言服务清理技术员笔记

3. **验证：**
   - 数据质量规则：使用 Fabric 数据激活器确保传感器读数在预期范围内
   - 完整性检查：设备 ID 等关键字段不能为空
   - 一致性验证：交叉引用设备规格与实际传感器能力

**结果：**
- 数据处理时间从 3 天减少到 4 小时
- 数据质量得分从 67% 提高到 94%
- 创建了包含 230 万个维护事件的统一数据集，可用于 AI 训练

### 2. 实验：规模化的试错

这是你使用不同的数据、不同的提示、不同的模型等运行 LLM 解决方案的时候。我合作的客户最常问的问题之一是：我怎么知道我的数据是否适合 AI？答案是试错。有一些基本的指导方针，我们在上一节中讨论过，但在 AI 方面，试错极其重要。

#### 用于实验的 Azure 工具：

**Azure AI Foundry:**
- **用途：** 统一的生成式 AI 开发平台（原 Azure AI Studio）
- **能力：** 提示流设计器、模型库访问、评估指标、RAG 管道测试
- **用例：** 比较 GPT-4o vs Claude vs Llama 的响应、测试提示变体、RAG 优化

**Azure OpenAI Service:**
- **用途：** 访问具有企业控制和合规性的 OpenAI 模型
- **能力：** GPT-4o, GPT-4 Turbo, GPT-3.5 Turbo, DALL-E 3, Whisper, text-embedding-3-large
- **用例：** 基于公司数据微调模型、利用公司知识库实施 RAG

**Azure AI模型目录（通过 AI Foundry）：**
- **用途：** 访问来自多个提供商的多样化基础模型
- **能力：** Llama 3.1, Mistral Large, Phi-3, Cohere Command 和其他 50+ 模型
- **用例：** OpenAI 的高性价比替代方案、特定领域的专用模型

### 3. 评估：衡量关键指标

这是定义指标并观察变化如何影响它们的过程。与测试错误的传统软件不同，AI 评估需要衡量主观质量、准确性和业务影响。

#### 用于评估的 Azure 工具：

**Azure AI Foundry 评估：**
- **用途：** 生成式 AI 应用的综合评估套件
- **能力：** 内置指标（基于事实、相关性、连贯性）、自定义评估器、AI 安全评估
- **用例：** 自动为 RAG 响应的准确性打分、测试有害内容、衡量响应质量

**Azure Monitor + Application Insights:**
- **用途：** 跨 AI 应用跟踪应用性能和用户行为
- **能力：** 自定义指标、实时仪表板、异常检测、分布式追踪
- **用例：** 监控响应时间、代币使用情况、错误率、用户参与模式

**Azure AI 内容安全：**
- **用途：** 检测并过滤 AI 应用中的有害内容
- **能力：** 实时安全分类、自定义内容策略、严重性评分
- **用例：** 评估 AI 输出是否存在仇恨言论、暴力、色情内容，确保品牌安全

#### 评估指标框架：

**技术指标：**
- **准确性 (Accuracy)：** AI 响应在事实上的正确频率如何？
- **相关性 (Relevance)：** 响应是否解决了用户的问题？
- **连贯性 (Coherence)：** 响应是否结构逻辑清晰且可读？
- **基于事实 (Groundedness)：** 响应是否基于提供的源材料（针对 RAG）？

**业务指标：**
- **用户满意度：** 净推荐值 (NPS)、点赞/点踩评分
- **任务完成率：** 完成预期操作的用户百分比
- **效率提升：** 与人工流程相比节省的时间
- **成本降低：** 通过 AI 自动化降低的运营成本

**评估管道示例：**
```python
def evaluate_rag_response(question, response, source_documents):
    metrics = {
        "groundedness": check_citations_accuracy(response, source_documents),
        "relevance": score_relevance(question, response),
        "coherence": assess_readability(response),
        "completeness": measure_answer_completeness(question, response)
    }
    return metrics
```

### 4. 验证与部署：生产就绪

模型在生产环境中的表现如何？这是进行一系列 A/B 测试的时候，以确保 AI 系统在真实用户和真实数据下可靠运行。

#### 用于验证和部署的 Azure 工具：

**Azure Container Instances (ACI) / Azure Kubernetes Service (AKS):**
- **用途：** 在可扩展的容器中部署 AI 应用
- **能力：** 自动扩缩容、负载均衡、蓝绿部署
- **用例：** 部署 RAG 应用、托管自定义 AI 模型

**Azure API Management:**
- **用途：** 管理、保护和监控 AI API 端点
- **能力：** 速率限制、身份验证、使用情况分析、A/B 测试
- **用例：** 为 AI 服务创建安全端点、实施灰度发布

**Azure DevOps:**
- **用途：** AI 应用的 CI/CD 管道
- **能力：** 自动化测试、部署管道、发布管理
- **用例：** 自动化模型部署、在发布生产前运行评估测试

#### 验证策略示例：

**第一阶段：影子模式 (第 1-2 周)**
- 将新 AI 模型与现有系统并行部署
- 比较输出但不向用户显示 AI 响应
- 衡量性能差异并识别边缘情况

**第二阶段：金丝雀发布 (第 3-4 周)**
- 将 5% 的流量路由到新 AI 模型
- 监控错误率、响应时间、用户满意度
- 如果指标保持稳定，逐渐增加到 25%

**第三阶段：A/B 测试 (第 5-8 周)**
- 将用户按 50/50 分流到旧系统和新系统
- 衡量业务影响：转化率、任务完成率、用户参与度
- 进行统计显著性测试，每种变体至少 1000 名用户

**第四阶段：全面铺开 (第 9 周及以后)**
- 如果 A/B 测试显示有改进，则部署给 100% 的用户
- 保持监控和回滚能力
- 记录经验教训以用于未来的部署

### 5. 推理：生产中可靠的 AI

确保 AI 响应可靠、一致且延迟低。这涉及管理向最终用户实时提供 AI 模型服务。

- **能力：** 检测仇恨言论、暴力、色情内容、自残、自定义屏蔽列表
- **用例：** 在向用户展示之前过滤 AI 输出，遵守内容策略和法规

#### 性能优化：

### 7. 反馈：持续改进

我们如何在确保隐私和合规的同时获取用户反馈？用户反馈对于改进 AI 系统至关重要，但必须负责任地收集。

#### 用于反馈的 Azure 工具：

**Azure AI 语言服务：**
- **用途：** 分析用户反馈文本以获取见解和情感（文本分析的继任者）
- **能力：** 情感分析、观点挖掘、关键短语提取、实体识别
- **用例：** 自动分类用户反馈、识别常见抱怨、跟踪满意度趋势

**Azure AI 文档智能：**
- **用途：** 从用户反馈表单和文档中提取数据（表单识别器的继任者）
- **能力：** OCR、布局分析、自定义模型训练、常见表单的预构建模型
- **用例：** 处理手写反馈表单、从调查中提取结构化数据

**Azure Event Hubs:**
- **用途：** 实时反馈数据摄入和流分析
- **能力：** 流处理、实时分析、与 Fabric 和 AI 服务集成
- **用例：** 收集实时用户交互、反馈事件、行为数据

#### 反馈收集策略：

**隐式反馈（自动）：**
- **用户行为：** 点击率、阅读响应花费的时间、滚动模式
- **任务完成：** 用户在 AI 交互后是否完成了预期操作？
- **后续行动：** 用户是否询问了澄清问题或请求人工帮助？

**显式反馈（用户发起）：**
- **评分系统：** 1-5 星、点赞/点踩、有帮助/无帮助
- **文本反馈：** 用于详细反馈的可选评论框
- **类别选择：** “回复太长/太短/不正确/有帮助”

**隐私保护反馈：**
- **数据匿名化：** 在存储反馈之前移除个人标识符
- **聚合分析：** 报告趋势而不是个人响应
- **保留策略：** 90 天后删除详细反馈，保留聚合指标

## 真实案例：企业客户服务 AI

### 公司：全球软件公司
**挑战：** 用 AI 替代 40% 的一级客户支持，同时保持客户满意度在 4.0/5 以上。

### LLMOps 实施：

#### 1. 数据策划 (第 1-2 个月)
**数据源：**
- 来自 Salesforce 的 230 万张历史支持工单
- 产品文档（847 篇文章，12 种语言）
- 知识库文章（2,156 个 FAQ 条目）
- 聊天记录（89 万次对话）

**Azure 实施：**
- **Azure Data Factory:** 自动从 Salesforce、SharePoint 和聊天系统进行每日提取
- **Microsoft Fabric:** 使用 Spark 笔记本处理和清理文本数据，移除 PII，标准化格式
- **Microsoft Purview:** 编目数据源，跟踪血缘，确保符合数据治理策略

**结果：** 在 Fabric OneLake 中存储了 320 万次客户交互的统一数据集，可用于 AI 训练

#### 2. 实验 (第 2-3 个月)
**进行的测试：**
- 针对常见支持场景的 12 种不同提示模板
- 针对不同查询类型比较 GPT-4o vs GPT-4 Turbo vs Llama 3.1 70B
- 针对产品特定知识的 RAG vs 微调方法
- 知识库文章的 5 种不同分块策略

**使用的 Azure 工具：**
- **Azure AI Foundry:** 使用提示流进行系统化提示测试和模型比较
- **Azure OpenAI:** 访问 GPT-4o 和 GPT-4 Turbo 模型
- **Azure AI 模型即服务:** 测试 Llama 3.1 和 Mistral 替代方案

**关键发现：** 使用 512-token 分块的 RAG 配合 GPT-4o 达到了 89% 的准确率，而 GPT-3.5 仅为 67%。

#### 3. 评估 (第 3-4 个月)
**定义的指标：**
- **准确性：** 人类专家审查 1,000 个随机响应（目标：>85%）
- **解决率：** 无需人工升级即解决的工单百分比（目标：>70%）
- **客户满意度：** 交互后调查（目标：>4.0/5）
- **响应时间：** 端到端延迟（目标：<3 秒）

**Azure 实施：**
- **Azure AI Foundry:** 使用内置指标和自定义 AI 裁判进行自动评估
- **Application Insights:** 实时性能监控和用户行为分析
- **自定义评估管道：** 人工审核员验证 AI 裁判的得分以进行质量保证

**结果：** 87% 的准确率，2.1 秒的平均响应时间，4.2/5 的客户满意度

#### 4. 验证与部署 (第 4-5 个月)
**部署策略：**
- **第 1 周：** 对 100% 的工单进行影子模式（生成 AI 响应但不显示）
- **第 2-3 周：** 5% 的非关键工单路由到 AI
- **第 4-6 周：** A/B 测试，25% AI vs 75% 人工座席
- **第 7-8 周：** 逐渐铺开到 40% 的一级工单

**Azure 基础设施：**
- **AKS 集群：** 根据需求从 3 个节点自动扩展到 15 个节点
- **Azure API Management:** 速率限制、身份验证、监控
- **Azure DevOps:** 具有回滚能力的自动部署管道

**结果：** 成功部署，正常运行时间 99.2%，人工工作量减少 34%

#### 5. 推理 (第 5 个月及以后)
**生产架构：**
- **Azure OpenAI:** 使用预配吞吐量单位 (PTUs) 的主要模型服务，以确保存量
- **Azure Redis Cache:** 常见查询的缓存命中率达到 67%，降低了成本和延迟
- **Azure AI 内容安全:** 对所有响应进行实时过滤，确保品牌和安全合规

**性能指标：**

## LLMOps 的关键成功因素：

1. **Start Small:** 从一个用例和经过验证的工具开始，然后再扩展
2. **Measure Everything:** 从第一天开始进行全面监控
3. **Business Alignment:** 将技术指标与业务成果联系起来
4. **Iterative Improvement:** 定期实验和优化
5. **Cross-Functional Teams:** 纳入领域专家，而不仅仅是技术人员
6. **Compliance First:** 从一开始就建立隐私和安全

LLMOps 不仅仅关于工具——它是关于创建一个系统的方法来构建、部署和维护 AI 系统，在管理概率性 AI 系统的独特挑战的同时，提供持续的业务价值。
